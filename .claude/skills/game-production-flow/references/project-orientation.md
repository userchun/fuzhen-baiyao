# 项目诊断与阶段总览

首次启用、接手陌生项目或用户要求重新评估进度时读取。目标是让用户看清全流程、目前位置，以及下一步为什么值得做。

## 先检查项目

先做与判断阶段相关的只读检查：
- 项目约束、现有任务与明确延期项、已确认玩法与验收条件。
- 引擎/框架、源码与资源目录、实际运行入口和现有构建/验证命令。
- 当前功能的关键实现、资源引用、存档路径，以及已有测试、实战和设备验证记录。
- 工作区改动与归属；不覆盖未知改动，不把未提交等同于未完成。

按现有证据定位后再读关键文件，不在启动诊断时遍历全部源码或运行耗时构建。没有项目目录或读取能力时说明限制，只索取定位项目所需的信息；不臆造引擎、文件路径或进度。

## 判断阶段

以 workflow.json 的全部12个环节为总览，以 workflow.md 的产物和通过条件为判断依据：
- 每个环节标记“未开始 / 进行中 / 待验证 / 已完成 / 阻塞 / 明确延期 / 不适用 / 未知”之一，并简述证据或缺口。
- 未找到证据标记“未知”，不能据此断言“未开始”。“不适用”需要说明原因。
- 设计已确认、素材已生成、代码已接入、自动检查通过、真实试玩通过和真机通过是不同证据。
- 已完成以当前范围和验收条件为准；历史记录要说明版本或时间限制。不要编造完成百分比。
- 同时说明“项目整体”和“本次功能”的位置。例如项目已有可玩版本，本次伙伴功能仍处于05素材、07接入与08存档阶段；已有性能检查也不代表所有功能均已验收。
- 阻塞和明确延期保持独立，不因为后续阶段存在产物就将前序环节补标为完成。

## 首次面向用户的输出

先给结论，再给总览和行动建议。以下是结构参考，不要将占位符或虚构示例当成实际诊断：

### 项目判断
简述项目类型、引擎与运行入口、已有可玩范围、主要缺口及证据限制。能提供来源时使用真实文件链接或验证记录。

### 阶段总览
从 workflow.json 读取全部12个环节，逐行展示：

| 阶段 | 状态 | 当前证据 / 尚缺什么 |
| --- | --- | --- |
| 阶段编号与名称 | 判断后的状态 | 具体实现、文件或验证依据；证据不足则说明 |

表格之后明确标出：
- **项目当前重点**：主要阶段或并行阶段，以及优先解决的缺口。
- **本次功能位置**：用户指定功能的当前环节；未指定时说明当前诊断范围。

### 推荐下一步
给出一个首选动作，说明：
1. **做什么**：具体功能或缺口，避免“继续完善游戏”等泛化建议。
2. **为什么先做**：已确认优先级、依赖关系或对可玩闭环的影响。
3. **完成后得到什么**：可评审的产物与对应阶段变化。
4. **怎么验收**：可观察的运行结果、已有检查或实战步骤。
5. **后续顺序**：必要时列出接下来的1—2项依赖动作；保留延期事项。

推荐从已授权、依赖满足且最能补齐当前闭环的动作开始，不机械选择编号最小的环节。优先执行用户明确指定的功能；若存在阻塞，说明影响并推荐可独立推进的动作。需重大玩法决策或权限时，提出具体方案及必要问题，不用开放式“你想先做哪项”替代推荐。

## 后续对话

- 仅启用、分析或了解进度：展示总览和建议后结束，不擅自修改游戏。
- 已授权实现或继续：展示诊断后立即推进首选动作；授权只覆盖用户请求的范围。
- 用户说“继续”：承接已确认范围和既有推荐，先说当前阶段、将做动作及下一验收点，再执行；不要重新要求用户选择。
- 步骤完成：更新同一待办和证据，简述“完成什么 → 现在处于哪一阶段 → 下一步”。存在可执行的已授权事项就继续，不以进度说明代替实际推进。
