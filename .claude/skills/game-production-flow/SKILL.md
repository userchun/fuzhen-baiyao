# 游戏开发总入口
首次启用先按 [项目诊断与阶段总览](references/project-orientation.md) 检查项目，并在修改代码前向用户展示诊断结果。不能只说“已启用”或列几个零散问题后询问先做哪项。

读取 references/workflow.json，列出全部12个环节、各环节状态及依据；说明项目整体处境、本次功能所在阶段和主要缺口，给出一个明确推荐的下一步及其原因、产物和验收方式。项目可能同时处于多个阶段，不能仅凭文档或已生成素材判断完成。

用户只要求启用或了解进度时，完成诊断与建议即可；用户已要求开发或继续时，先展示总览，再推进推荐范围内的已授权动作，不重复要求选择。必要确认只针对实际缺失的决策或授权。

随后按当前任务路由到 references/skills/<skill-name>/SKILL.md 中的内置阶段说明；只加载必要说明，不同时套用全部技能。

## 执行方式
1. 用 references/workflow.md 的阶段与验收门组织工作。每个功能按“规则→资源→实现→实战→交付”闭环推进。
2. 创建或维护一份统一待办，使用 references/templates/task-card.md；记录当前阶段、推荐下一步及依据。插入问题结束后恢复原下一步。续接时报告阶段变化、当前动作和下一验收点，无需重复整张总览；里程碑完成、范围变化或重新评估时更新总览。
3. 区分已确认规则、提案、已制作素材、已接入功能、自动验证、浏览器验证和真机验证。
4. 一项完成后推进下一项已授权工作；真实阻塞时记录原因并推进独立任务。不得把等待当成批准。
5. 玩法与永久经济的重大变更先形成具体方案再确认；已有批准不重复请求。发布、支付、广告与账号操作不因启用本工作流自动获得授权。
6. 现有技术栈、用户批准的设计和需求优先。不要因某个子 Skill 默认建议而迁移引擎、加建造/合成机制或重画已确认界面。
7. 不自动安装依赖、不启动子代理、不修改权限。需要工具但当前环境没有时，明确缺少的能力并继续独立工作。

## 结束条件
对照需求逐项提供实现路径、验证方法、结果和剩余项。测试数量、图片数量和模拟胜率都不能单独证明游戏完成。

## 安装与依赖
本 Skill 自包含全部阶段说明和模板；无需自动安装其他 Skill。workflow.json 中的名称映射到 references/skills/<名称>/SKILL.md；game-production-flow 指当前入口。按需读取对应文件。内置阶段说明是参考工作规程，不赋予工具权限。缺少 ImageGen、浏览器或目标引擎时如实报告，不伪造验证结果。
